## Proposed backend interfaces (logical names, NOT deployed routes)
1. Action summary (authenticated current workspace/scope): items [{kind, available, count|null, required, description?}], explicit completeness/status. Allowlisted kinds video_review, performance_review, team_management, family_action, media_consent, my_videos. Count means distinct outstanding actions the current user may execute, not all pending records. No unauthorized names or IDs. Optional consent never required or counted. Server derives identity and verifies scope; client-selected team is only a filter, not authority. Count null/absent on unknown/unavailable, zero only successful complete result. Separate unavailable per kind where appropriate; no counts inferred from partial roster or paginated list. Server returns no-store.
2. Review inbox (authenticated current workspace/scope): validated team/player/category filters, bounded keyset pagination and stable ordering (created_at, id), authorized team/player options, items [{id, playerId, teamId, playerLabel, teamLabel, category, status:'pending', can_review:true, createdAt}], scoped unfiltered pendingTotal and filtered total or cursor/hasMore; distinguish count completeness. IDs opaque. If a submission is associated with several teams, define canonical review context and deduplicate count by actionable submission. Server must restrict to eligible Club Admin/Coach, same organization/team, current membership, no self-review even for dual-role, pending state, no unauthorized identifiers or private URLs. The backend must recheck permission at playback and review; the UI is not authority. Map server field names only after contract agreement.
3. Existing per-player service/list and review-private remain the mutation and playback workflow, subject to current media gates. Do not change grants, endpoint paths or media behavior from UX branch. Existing success receipt is source of refresh signal. Thumbnail API, if proposed, must authorize the same row independently, return no public object URLs, and honor revocation; absent approved API use only demand-driven authorized local previews or placeholder.
4. Error semantics: 401 clear all identity state/sign-in; 403 clear affected scope and show generic denied; 404 stale row removed after refresh; 409 conflict refresh and do not retry mutation blindly; 503 disabled/unavailable, no stale counts. No automatic fallback. Any request belongs to identity + workspace + scope revision; discard late responses, abort on scope exit.
5. P1 future capability read model must separate can_view, can_download, can_publish, can_unpublish, own-consent action, effective publication, consent withdrawal and revocation. No consent from upload, coaching review, presence of another guardian, or membership alone. RBAC-05 to define authoritative multi-guardian rule. No live endpoint calls from prototype.
